# Autosave stall investigation + rotating autosaves (2026-11-26)

Branch `autosave-rotation` (off `main` at c470a01). Commits: b7983f1 (cheaper snapshot, `forceAutosave` hook),
204ae94 (rotating autosaves, metadata cache, honest stall timing), 7c261a2 (test), plus this doc.

## Part 1: the autosave stall

How it was measured: a scratch driver booted a private server (port 31517, a `mktemp -d` save dir,
`COLONY_TEST_HOOKS=1`, `COLONY_WORLD_SIZE=1024`, `COLONY_WORLD_SEED=7`). It fast-forwarded one game day at a time,
called the new `forceAutosave` test hook, and copied each save. Per-step timings came from temporary
`performance.now()` probes in `writeSave` / `saveFileFor` / `diffTilesForSave` / `pruneBaseFiles`, which were removed
before committing. The scratch saves were about 1.36 MB. The user's are 3.7 MB, so their absolute numbers are about
2.7 times larger, but the split is the same.

### (a) Where the synchronous time went (before, HEAD c470a01)
| step (1024 world, ~1.36 MB save) | ms |
|---|---|
| `diffTilesForSave` sync part (`sameBytes` biomes + `encodeDiffs`) | 2.3 - 3.6 (one 13) |
| `snapshotWorld` | 9.3 - 12.3 |
| of which `owners: Array.from(tileOwner).flat()` (~90k NPC tile-owner pairs, 712 KiB, 52% of the file) | 6.5 - 12 |
| of which base64 of full tiles + biomes, thrown away again for a diff save | 0.6 - 5 |
| `JSON.stringify` | 3.6 - 5.1 |
| `pruneBaseFiles`: a full `JSON.parse` of EVERY slot file, after every streamed save | 4.9 - 8.5 per 1.36 MB file |

Two more findings:
- **The logged "snapshot+stringify ... (blocks the tick)" number was inflated.** Its clock started before
  `await diffTilesForSave()`, which awaits `fsp.access` (and gzips the base file on the first save). Sim ticks run during
  that await, and a 1024-world tick costs 20-40 ms, so they were counted as save stall. That explains the noisy 16-63 ms.
  The first save also showed 95.8 ms because it covered the base-file gzip.
- **The "total" included `JSON.parse` of the slot files**, and those parses block the event loop too, just in a later
  turn. With a 3.7 MB autosave plus a `slot1.json`, that is roughly 2 x 15-25 ms, which is where the 89-199 ms totals came from.

### (b) What grows each autosave
These are scratch reproductions, not the user's save (the user's real saves were not read or touched). Per-field JSON
sizes come from the two runs below (`scripts/save-field-sizes.mjs`):
- **Raids on, colony undefended (seed 7):** +3 to +12 KiB per day (1355 to 1523 KiB over 24 days), and the rate keeps rising. The Town Center fell on
  night 1. After that, every nightly raid group stays `state: "marching"` with no goal (`raidMarchGoal` returns null:
  "nothing targetable, e.g. all warded, means hold position") and holds still forever. Over 25 days: 44 raid groups and
  192 raid mobs. `mobs` grew by about 5.7 KB a day and `raidGroups` by about 1.7 KB a day. Each held raider costs about
  0.6 KB, each group about 0.9 KB.
- **Raids off (same seed):** +0.2 to +0.9 KiB per day. That is `chronicle` (capped at `CHRONICLE_MAX = 120` entries),
  `sites` and `gates` changing. It is bounded.
- No field is serialised twice. `owners` (712 KiB), `regionPlan` (74 KiB), `zones` and `homeDesigns` are large but
  constant.

### (c) Bounded?
Normal state is bounded. The unbounded part is **game behaviour, not a save bug**: raid groups that can never target
anything keep accumulating. That happens when there is no Town Center, or plausibly when everything is warded. Fixing
it would change raid rules, so it is **not fixed here**. The user's +52 KiB per autosave is about 75 raiders' worth a
day, which is consistent with this but not proven. To check it on the real game, copy two kept autosaves (for example
`autosave-50.json` and `autosave-55.json`) somewhere else and run
`node scripts/save-field-sizes.mjs copy-50.json copy-55.json`. If `mobs` / `raidGroups` dominate the growth and the raid
group count climbs, this is it.

### (d) What was changed (behaviour-preserving, same save format)
1. `owners` / `tileClans` are flattened in one loop (`flatPairs`: same array, same order).
2. A diff save no longer encodes full tiles / biomes / explored only to discard them (`snapshotWorld(diffLayer)`).
3. Save metadata (the list entry plus the base file it needs) is cached per file by inode + size + mtime, and primed from
   the object a save just wrote. Pruning and `listSaves` no longer parse unchanged files. This also stops retained
   autosaves from adding per-save cost.
4. The base-file await (`prepareDiffSave`) runs before the timed section, and `diffTilesForSave` is now synchronous, so
   the log line `diff+snapshot+stringify N ms (blocks the tick)` measures only the real stall.

After (same seed, 1024 world, ~1.36 MB):
| | before | after |
|---|---|---|
| snapshot (`saveFileFor`) | 9.3 - 16 ms | 3.3 - 6.9 ms |
| sync stall (diff + snapshot + stringify) | ~15 - 25 ms (logged, inflated: 15 - 34) | 9.3 - 13.4 ms steady (first 2-3 saves 16 - 34 while the JIT warms up) |
| prune | 7.6 - 24 ms (parses every slot file) | 0.4 - 1.0 ms (no parse) |
| total | 29 - 54 ms | 14.5 - 20 ms steady |

Stringify (about 4-5 ms) is still the irreducible part on the tick. Recommended next steps if the stall still matters on
3.7 MB saves:
- Cache the JSON of large unchanging fields (`owners`, `regionPlan`, `zones`, `homeDesigns`) behind a dirty flag. This
  needs every `tileOwner` mutation to bump a version, so it is a riskier change than the ones above.
- Fix the raid accumulation (game-rule decision). That stops the growth itself.

## Part 2: rotating autosaves

- Each normal-game autosave writes `<SAVE_DIR>/autosave-<n>.json` using atomic temp + rename. The SIGTERM / SIGINT /
  quit shutdown save is included, and now also uses temp + rename. `n` continues from the highest canonical
  `autosave-<n>.json` on disk at boot (it is read once, then counted in memory, so a number is never reused even after a
  failed write).
- Creative games still autosave to the single `creative` slot. Manual saves into `autosave` or `autosave-<n>` are refused.
- **Retention after save n is written:** keep every multiple of 10, the latest multiple of 5 that is not a multiple of 10
  **and comes after the last multiple of 10 at or below n**, and n itself. Delete the rest. Worked examples:
  - 48: 10 20 30 40 45 48
  - 50: 10 20 30 40 50 (45 goes)
  - 55: 10 .. 50 55
  - 56: 10 .. 50 55 56
  - 62: 10 .. 60 62 (55 goes)

  Note on the spec: read literally, rule (2) keeps 45 at save 50. The user's own example drops it, so the "since the
  last multiple of 10" reading is the one implemented. Multiples of 10 are kept forever, so the file count grows by one
  every 10 autosaves (about 10 days of play).
- Only names matching `^autosave-[1-9]\d{0,8}\.json$` are ever deleted. That is stricter than `^autosave-\d+\.json$`, so
  `autosave-07.json` is left alone. Slots, `creative.json`, the old `autosave.json`, base files and anything else are
  never touched.
- Base cache files: `pruneBaseFiles` keeps the base of every save on disk (fixed slots and every kept autosave) plus the
  world in memory. It runs after every streamed save and also after any save whose rotation deleted something. The
  shutdown save (full arrays) does not prune; the next streamed save does.
- Protocol: `SaveSlot = FixedSaveSlot | \`autosave-${number}\``. The shared helpers are `isSaveSlot` (strict, no
  traversal), `autosaveNumber` and `saveSlotLabel` ("Autosave 48", "Autosave (old)", "Slot 1"). `savePath` throws on
  anything else. `SaveInfo.autosave` holds the number.
- `listSaves`: numbered autosaves newest first, then the old `autosave.json` as "Autosave (old)" (if present), then slot1-3
  and creative. In the menu, Continue loads the newest numbered autosave, or the old file if there are none. The load
  lists show every save.

Files: `server/src/autosaves.ts` (new: rule + counter), `server/src/saves.ts`, `server/src/worldbase.ts`,
`server/src/testhooks.ts` (`forceAutosave`), `server/src/constants.ts` (`SAVE_SLOT_LABELS` removed),
`shared/src/protocol.ts`, `client/src/menu.ts`, `client/src/main.ts`, `server/autosave-rotation-test.mjs` (new),
`server/save-load-test.mjs` and `server/creative-test.mjs` (updated for numbered files), `scripts/save-field-sizes.mjs` (new).
